What you get

Built for the part everyone else leaves to you.

Connecting a model to a database is the easy half. The governance around it — who asked, what ran, what came back, and how you prove it later — is the half that keeps the project out of production.

Your data, where it already lives

Connect the databases you already run. No migration, no consolidating everything into one warehouse first, and nothing copied to a vendor you have to trust.

REST, SQL and MCP at once

Point Claude, Cursor or any MCP client straight at it — current with the 2026-07-28 spec, older clients still welcome. In VS Code, the free TDB extension connects it in one command. Call the same source over REST and get the same JSON, value for value: exact decimals, binary data as base64, timestamps in ISO 8601. Or connect Metabase, DBeaver and other Postgres clients unchanged. Read-only is enforced before a statement reaches the engine.

An audit log you own

Every query, every result, every AI tool call — recorded on your own infrastructure in a tamper-evident hash chain. Even the free edition writes one.

Inside your perimeter

Runs in one Docker command on infrastructure you control. Your data never leaves it, and OAuth 2.1 with PKCE, RBAC and per-key rate limiting keep access governed.

Lean by design

Every token an agent spends reading a result is one it can't spend on your question. Lean Mode cuts a 100-row answer from 10,412 to 6,868 tokens and a 30-table schema from 5,235 to 3,025, with the same answers on a 21-question check. Aggregates and filters run in the database, so an agent fetches the answer instead of the rows behind it, and a response that hit the row ceiling says so. Set it per call, per API key or server-wide. Nothing set means nothing changes.

Build or buy

What your team would otherwise build — and keep building.

Connecting one agent to one database takes an afternoon. Making it safe enough for production data, and keeping it that way as databases, clients and the MCP spec move, is a standing commitment. This is the part TDB takes off your roadmap.

  • Read-only, in five SQL dialects

    A check that reads SQL the way each engine does, plus read-only sessions at the source and refusal of over-privileged database roles. We published two security advisories for this layer in 2026; your own version would need the same scrutiny.

  • An audit log a reviewer accepts

    Hash-chained entries, refusals included, verification on demand, retention without deletion, and incremental export to Splunk or S3.

  • Keeping up with MCP

    Four protocol revisions served side by side, so an AI client upgrade doesn't break your integration — and the next revision is our job, not yours.

  • Identity and access

    API keys with rotation, JWT, OAuth 2.1 with PKCE for AI clients, roles, per-key tool scopes and rate limits.

  • Your BI tools, unchanged

    A PostgreSQL wire gateway, so Metabase, DBeaver and psql get the same governance and audit as the agents.

  • Patching, forever

    Eight security updates published since September 2026, each with what was exposed and what to do. See them all.

Your engineers keep the work only you can do — the agents and what they're for. TDB keeps the plumbing current.

The audit log

Not a checkbox. The reason this exists.

When an agent can query production data, "what did it actually do?" stops being a curiosity and becomes an audit question. TDB answers it by default, in a format you can hand to a compliance reviewer.

  • Hash-chained records — a removed or edited entry breaks the chain and is detectable.
  • Refusals are logged too, so a blocked write is evidence rather than silence.
  • Every MCP call names the AI client and protocol version that made it.
  • Retention by sealing, never deletion — segments stay independently verifiable.
  • Incremental export to Splunk or S3, so it lands in the SIEM you already run.
