The lifecycle

From a registered source to an audited answer.

Five stages, the same for every caller. Pick one to see what happens there.

Register a source once.

Point TDB at a database or a file. It keeps the credentials encrypted and gives the source a governed name; nobody downstream ever sees a connection string.

Registering sources →
  • PostgreSQL, MySQL, SQL Server, Snowflake, CSV and Parquet
  • A whole database or a single table
  • Credentials encrypted at rest, no plaintext mode

Decide who may ask what.

Each caller gets an identity and a scope. Every statement is checked as read-only before it runs, and the database session enforces it again.

Architecture & security model →
  • OAuth 2.1 with PKCE, API keys, JWT
  • Roles, per-key tool scopes, rate limits
  • Read-only checked the way each SQL dialect reads it

Answer on whatever protocol asks.

Agents speak MCP, scripts speak REST, BI tools speak Postgres. TDB answers all three from one governed surface, with the same values on each.

MCP reference →
  • MCP 2026-07-28 and earlier revisions, side by side
  • REST with an OpenAPI description
  • Postgres wire gateway for Metabase, DBeaver, psql

Send the answer, not the overhead.

Lean Mode shapes results for an agent's context window. Rows travel as arrays, schemas as types, and long text can be trimmed with a visible marker.

Keep the evidence.

Every query and every refusal is written to a log on your infrastructure, naming the caller and the AI client, and chained so an edit is detectable.

Audit log →

Why teams choose it

Production-safe AI access, without building it yourself.

Connecting a model to a database is the easy half. The governance around it is the half that keeps projects out of production.

01

Governed access, not raw credentials.

Agents get a key scoped to what they may ask — never your database password. Every statement is checked as read-only before it runs, and the database session enforces it again.

02

Answers, not token overhead.

Lean Mode sends results sized for the agent: about a third fewer tokens on large results, with the same answers. Aggregates and filters run in the database, so the agent reads the answer, not the rows behind it.

03

Evidence, not trust.

Every query, refusal and AI client is recorded in a log you own — even the free edition writes one. The commercial edition chains it so an edit is detectable, and exports it to the SIEM you already run.

Build or buy

What your team would otherwise build — and keep building.

Connecting one agent to one database takes an afternoon. Making it safe enough for production data, and keeping it that way as databases, clients and the MCP spec move, is a standing commitment. This is the part TDB takes off your roadmap.

  • Read-only, in five SQL dialects

    A check that reads SQL the way each engine does, read-only sessions at the source, and refusal of over-privileged database roles. We published two security advisories for this layer in 2026; your own version would need the same scrutiny.

  • An audit log a reviewer accepts

    Hash-chained entries, refusals included, verification on demand, retention without deletion, and incremental export to Splunk or S3.

  • Keeping up with MCP

    Four protocol revisions served side by side, so an AI client upgrade doesn't break your integration — and the next revision is our job, not yours.

  • Identity and access

    API keys with rotation, JWT, OAuth 2.1 with PKCE for AI clients, roles, per-key tool scopes and rate limits.

  • Your BI tools, unchanged

    A PostgreSQL wire gateway, so Metabase, DBeaver and psql get the same governance and audit as the agents.

  • Patching, forever

    Eight security updates published since September 2026, each with what was exposed and what to do. See them all.

Your engineers keep the work only you can do — the agents and what they're for. TDB keeps the plumbing current.

The audit log

Not a checkbox. The reason this exists.

When an agent can query production data, "what did it actually do?" stops being a curiosity and becomes an audit question. TDB answers it by default, in a format you can hand to a compliance reviewer.

  • Hash-chained records — a removed or edited entry breaks the chain and is detectable.
  • Refusals are logged too, so a blocked write is evidence rather than silence.
  • Every MCP call names the AI client and protocol version that made it.
  • Retention by sealing, never deletion — segments stay independently verifiable.
  • Incremental export to Splunk or S3, so it lands in the SIEM you already run.

The Data-Bridge in 60 seconds

Recorded against the published tdb-community 0.13.0 image: every response on screen is real output. No sound.

Step 1 of 5 · Register

Point TDB at the data you already have.

One call registers a source under a governed name. Credentials are encrypted; nothing is copied.

POST /v1/sources
{"name": "orders", "source_type": "postgres", "connection": {…}}
Step 2 of 5 · Connect

Give an agent a key, not a password.

Claude, Cursor or VS Code connect to one MCP endpoint. The key decides which tools the agent may use.

https://tdb.example.com/v1/mcp
Authorization: Bearer tdbk_…   (role: read, tools: query_source)
Step 3 of 5 · Govern

Every statement is checked before it runs.

Read-only is checked the way the database reads SQL, then enforced again by the session. A write is refused — and recorded.

DELETE FROM orders …
→ refused: sql_validation_failed (audited)
Step 4 of 5 · Lean

The agent gets the answer, not the overhead.

With Lean Mode, rows travel as arrays and schemas as types. Same answers, about a third fewer tokens on large results.

{"columns": ["region", "growth"],
 "rows": [["EMEA", 0.18], ["APAC", 0.11]],
 "lean": {"format": "table"}}
Step 5 of 5 · Audit

And you keep the evidence.

Each call is chained into a log on your infrastructure, naming the caller and AI client, ready for Splunk or S3.

 "rows_returned": 2, "seq": 4127, "hash": "e70a…"}
